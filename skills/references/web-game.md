# 웹게임 기획서(GDD) 구조

브라우저 환경(WebGL, HTML5 등)에서 실행되는 게임을 전제로 한다. 세션 길이, 로딩 시간, 입력 방식(마우스/터치 위주) 같은 웹 특유의 제약을 항상 염두에 두고 작성한다. 프로젝트 규모에 맞춰 섹션을 가감한다 — 소규모 싱글 플레이 게임이라면 7번(리텐션)은 생략해도 된다.

## 1. 게임 개요
- 한 줄 컨셉 (elevator pitch)
- 장르 및 레퍼런스 게임 (비슷한 느낌의 기존 게임 1~2개, 뭘 차용하고 뭘 다르게 할지)
- 타겟 플레이어층
- (BM 가정) 무료 실험작인지 상업적 목적인지, 상업적이라면 광고/IAP/배틀패스 중 방향 감을 여기서 한 줄로 잡아둔다 — 9번에서 구체화한다.

## 2. 코어 루프 (Core Gameplay Loop)
플레이어가 반복적으로 수행하는 가장 기본적인 행동 사이클을 화살표로 정리한다.
예: 탐험 → 전투 → 보상 획득 → 강화 → 다시 탐험

이 루프가 왜 재미있는지, 무엇이 플레이어를 계속 이 루프로 끌어당기는지 한두 문장으로 설명한다. 코어 루프가 명확하지 않으면 나머지 시스템을 아무리 정교하게 짜도 게임이 붕 뜬다 — 이 섹션을 가장 먼저, 가장 확실하게 정한다.

## 3. 핵심 메카닉
게임의 규칙과 조작 방식. 이동, 전투, 퍼즐, 빌딩 등 실제 플레이 동작을 구체적으로 정의한다.
- 플레이어가 할 수 있는 행동 목록
- 각 행동의 입력 방식과 결과
- 승리/패배(혹은 성공/실패) 조건

## 4. 진행 시스템 (Progression)
플레이어가 시간이 지나며 무엇을 얻고 어떻게 성장하는지.
- 성장 축 (레벨, 스킬 트리, 장비, 컬렉션 등)
- 각 성장 단계에서 플레이어에게 주어지는 새로운 선택지나 능력

## 5. 밸런싱
표로 정리한다:

| 항목 | 획득처 | 소모처 | 기준값/비고 |
|---|---|---|---|
| (재화/자원명) | | | |

정확한 최종 수치보다, "이 수치를 어떤 기준과 논리로 정할지"를 먼저 세운다 (예: "레벨당 필요 경험치는 이전 레벨의 1.15배로 증가"). 난이도 곡선이 있다면 초반/중반/후반 체감 난이도를 간단히 서술한다.

## 6. 콘텐츠 구조
스테이지/레벨/맵이 어떻게 구성되고 초기 출시에 몇 개 정도 필요한지, 이후 콘텐츠를 어떤 주기·방식으로 확장할지.

## 7. 리텐션 & 라이브옵스
플레이어가 다음 날, 다음 주에도 돌아오게 만드는 장치.
- 일일/주간 퀘스트, 로그인 보상
- 이벤트 주기, 시즌 개념
- (소규모/싱글 플레이 프로젝트라면 이 섹션은 생략 가능)

## 8. 웹 플랫폼 제약
웹게임 특유의 현실적 제약을 명시한다.
- 목표 세션 길이 (짧은 브라우저 세션을 고려한 설계인지)
- 초기 로딩 시간 목표, 에셋 총 용량 상한
- 사용할 기술 스택 (Phaser, Unity WebGL, PixiJS, Three.js 등) — 정해졌다면 명시하고, 그 선택이 코어 루프 구현에 미치는 제약도 짚는다
- 모바일 브라우저 대응 여부 (터치 입력, 화면 비율)

## 9. 수익화
상업적 목적이라면 다른 섹션과 동등한 비중으로 다룬다 — 무료 실험작이면 이 섹션은 짧게 줄이거나 생략해도 된다. 모델 종류와 장르 궁합은 `bm-game.md` 참고. 더 깊게 설계해야 하면(무과금-과금 격차, 결제 유도 지점, 지표) Game-BM 스킬을, 실제 수치로 그 격차를 만들어야 하면 Game-Balance 스킬을 사용한다.

- **주 수익원 / 보조 수익원**: 광고(전면/보상형), IAP(시간 단축/코스메틱/컨텐츠), 배틀패스 등 중 조합을 정한다
- **결제 유도 지점**: 플레이 중 어느 시점에 자연스럽게 등장하는지
- **무과금 유저 도달 범위**: 결제 없이 전체 콘텐츠의 어느 정도까지 무리 없이 진행 가능한지

## 10. 아트 & 톤
비주얼 스타일, 분위기를 한두 문장으로 정리한다. 상세 아트 디렉션(레퍼런스 이미지, 색상 팔레트 등)은 필요시 별도 문서로 분리해도 된다.
